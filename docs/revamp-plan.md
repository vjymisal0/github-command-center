# OSS Tracker revamp plan (security-first)

Status: proposed, not implemented. Scope: the deployed multi-user application, not just a visual refresh. Based on repository inspection; production configuration and exposure have not been verified.

## Incident first — before the redesign

1. Treat the observed cross-account display as a potential private-data incident. Restrict the deployed app to trusted users or take it offline until isolation is verified. Ask affected users to revoke PATs; rotate GitHub OAuth/client secrets and credential-encryption keys if exposure is suspected, with a deliberate decrypt/re-encrypt or token-reconnection procedure. Preserve relevant access logs and backups securely; assess which private metadata was visible and notify affected users as appropriate. Do not publish logs or tokens.
2. Back up Postgres and any `.dev-store.json` before changing data. Audit for plaintext PATs in the store, backups and logs; never copy them into fixtures. Disable new signups/connections while investigating.
3. Release only after two independent accounts pass the isolation gate below. A theme refresh must not delay this fix.

## Verified root-cause candidates in this checkout

- `apps/api/src/main.ts`: `memoryRepos`, `memoryPrs` and `totalMergedPrsCount` are module-wide, persisted in `.dev-store.json`. `syncGitHubData` merges every user's GitHub records into these arrays. List endpoints check whether *this user* has a connection, then return the *shared* arrays; detail and description endpoints do not even check the user's repository entitlement. Inbox and analytics likewise use shared data. Disconnecting one account resets everyone's arrays.
- Login auto-registers any email/password and falls back to permissive in-memory login after any database error. The cookie is unsigned and lacks a production `secure` setting in the password flow. OAuth state maps to a user ID but is not bound to the initiating browser session; its callback writes that ID into the memory session map as if it were an email. `connectionState` has a `memory_admin` default. These paths need replacement, not another client-side filter.
- PATs are retained in process memory and serialized **in plaintext** to `.dev-store.json` even though an encrypted DB credential also exists. `packages/shared/src/crypto.ts` and Compose have fixed/default key fallbacks. `@fastify/cors` accepts arbitrary origins with credentials. The current browser PAT request does not request cross-origin credentials. `apps/api/src/api.test.ts` expects unauthenticated data endpoints to return 200, contradicting the auth hook. The worker writes DB records, but the API serves the unrelated memory arrays; there is no dependable worker-to-API read path.
- Webhook handler updates shared PRs by PR number alone, without repository identity; signature validation is based on reserialized JSON, not raw bytes. Nonproduction accepts invalid signatures. These are separate trust-boundary failures.

## Target architecture (reuse existing stack)

Keep Next.js, Fastify, Prisma/Postgres, Octokit, and the existing worker only if it demonstrably improves sync throughput. No new framework or UI library. Postgres is the only source of truth for sessions, connections, entitlements, PRs and counts; remove fixture and disk-store fallbacks from live routes. Treat GitHub `Repository`/`PullRequest` as canonical shared records **internally**, but grant read access only via active `UserRepositoryAccess` for the authenticated user and active connection. An external authored public PR is visible only after a verified user-specific contribution link/entitlement; public search results alone never authorize private repository data. All list, detail, description, search, inbox and aggregate queries must join through this entitlement; return 404 for unauthorized object IDs, 401 for absent sessions. Validate session/connection ownership at mutations and at job execution. Never use an ID or login from request input as the authority.

### Phase 1 — containment and failing tests (release blocker)

- Create two users A/B with different private repos/PRs plus a deliberate shared public repo. Exercise every read surface (`/repositories`, `/:id`, `/pull-requests`, `/:id`, `/:id/description`, `/inbox`, `/analytics/overview`, connections and sync status). Verify no A-only ID, title, description or count appears to B, even via guessed IDs or after B connects, syncs, or A disconnects. Anonymous requests must get 401. Verify shared public records are visible only under each user's own verified entitlement. Include web SSR responses and cache headers in this gate.
- Add a regression for concurrent syncs, stale access after connection deletion/revocation, and webhook changes to similarly numbered PRs in separate repos. First prove the current behavior fails; do not use real tokens in tests.

### Phase 2 — identity and storage repair

- Remove runtime fixture/global-cache/store fallback from production paths, and delete plaintext PAT persistence. Migrate only attributable records: derive ownership from authenticated connection/GitHub identity plus independently verified repo permissions. **Do not auto-assign ambiguous mixed shared-array records.** Quarantine/purge them after backup and ask users to re-sync. Keep migration reversible via a tested Postgres backup/restore; do not destroy existing user accounts without an explicit mapping plan.
- Make DB unavailability a 503, never a successful login. Disable auto-signup on login; use explicit invite/registration policy (default invite-only) or verified GitHub sign-in. Replace demo admin/password bootstrap with one-time secure operator setup. Store password hashes with random per-user salts and approved parameters if local passwords remain. Session cookie: opaque random ID, HttpOnly, Secure under HTTPS, SameSite, host-only scope, expiry and server-side logout/revocation; rotate at login. Bind OAuth state to initiating authenticated session, short expiry and one-time use; decide explicitly whether GitHub authorization connects an account or signs a user in. Do not infer identity from a callback state alone.
- Require a strong encryption key at production startup; encrypt credentials only, migrate/revoke any plaintext tokens, and ensure backups/key-rotation procedure. Never return connection IDs containing user identifiers when unnecessary. Use same-origin API proxy or narrow exact CORS origins, CSRF protection for cookie-authenticated mutations, and rate limits for login/token validation.

### Phase 3 — one authoritative sync path and access lifecycle

- Connect PAT: validate GitHub identity and granted access; store encrypted credential and owned connection atomically; enqueue user+connection-scoped sync (or keep synchronous sync until worker is proven necessary). Worker checks ownership/status before decrypting and writing; all writes populate DB repository, PR, access and action tables. API reads those tables only. Paginate GitHub results, record partial coverage and actual last-successful-sync timestamps; do not manufacture CI=Passing, review or merged totals from incomplete data.
- Multiple connections per user: record which connection grants a repo; when one is removed retain access only if another verified active grant remains. Disconnect/revocation immediately hides inaccessible records, stops jobs and deletes that user's credentials; prune orphaned private canonical records after grace/backup policy. Refresh entitlements on each sync. Return useful failure states instead of swallowing exceptions.
- Webhooks: verify HMAC on raw bytes in all environments, deduplicate deliveries, resolve by GitHub repo ID and PR ID/number, re-fetch authorized data, and update only entitled users' derived inbox records. Do not let a webhook grant visibility.

### Phase 4 — interface and design alignment

- Reference: `../portfolio-vijay/app/globals.css` and `../portfolio-vijay/app/layout.tsx` (local source for vijaymisal.tech; check deployed site separately before calling it identical). Match portfolio typography with **Geist Mono** as the main body/headline face (`--font-mono`); use **Outfit** only for optional display accents and **Inter** for dense tables if legibility requires it. Load through `next/font/google` at build or bundle assets for self-hosting; retain system fallbacks.
- Copy the portfolio's semantic HSL palette rather than the current pink/purple token scheme: light background `hsl(42 33% 97%)`, foreground `hsl(222 35% 12%)`, primary `hsl(221 70% 35%)`, accent `hsl(17 85% 54%)`; dark background `hsl(222 47% 7%)`, foreground `hsl(210 40% 96%)`, primary `hsl(32 95% 58%)`, accent `hsl(187 82% 53%)`. Preserve status colors with measured contrast and text labels; set theme preference/system fallback and accessible focus states.
- Rework the current shell and existing Overview, Inbox, PR list/detail, repository list/detail, and Connections views around trustworthy per-user state: signed-in identity, accessible account switch/context, accurate empty/partial/stale states, responsive navigation, keyboard access and no leaked records in pre-rendered HTML or search. Reuse components already in `apps/web/app`; avoid a wholesale component-library migration.

### Phase 5 — verification and staged rollout

- Run unit/integration tests with isolated Postgres fixtures, a two-browser E2E test for A/B isolation, authorization matrix for every endpoint, CSRF/CORS/cookie/OAuth checks, malformed webhook tests and credential redaction checks. Run build/typecheck/tests and manual desktop/mobile/light/dark accessibility checks. Verify that SSR fetches are per-request (`cache: 'no-store'` is already used), that errors do not masquerade as empty results, and that logout invalidates all surfaces.
- Stage: private staging environment with synthetic accounts → migrate/clean data → shadow compare per-user counts against GitHub → restricted canary → production. Roll back code and database together from tested backups; never restore the insecure shared store. Reopen public access only once cross-user tests pass in staging **and** production with two separate accounts and a direct guessed-ID attempt. Track auth failures, sync failures and unexpected cross-user access without logging private data.

## Done when

Two distinct production users can connect accounts and independently browse all routes without seeing each other's private titles, descriptions, counts, tokens or connection metadata; unauthenticated and unauthorized direct requests are blocked; connection revocation removes access immediately; no plaintext credentials remain in runtime stores/backups under operator control; the interface uses the verified portfolio typography and light/dark palette and meets keyboard/contrast basics. Document any residual historical exposure and remediation before declaring the incident closed.
